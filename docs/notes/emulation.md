# pico-amiga: what was not obvious in the emulation

## Musashi

- `external/musashi/gen/` is generated by `tools/gen_musashi.py`; never edit it.
  Local changes to Musashi are marked `PICO-AMIGA PATCH` (m68kcpu.c) and
  `PICO-AMIGA:` (m68kconf.h). Re-run the generator after touching m68k_in.c or
  m68kconf.h or tools/musashi_hot*.txt (the 250 hottest handlers, placed in
  SRAM; musashi_hot_020.txt: the 68EC020's, from AGA runs; the generator
  also orders m68ki_handlers[] by it and emits per-handler
  cycles, which m68k_execute() uses instead of the 64 KB opcode table). The
  handlers are compiled twice, gen/m68kops.c for the 68000 and gen/m68kops_020.c
  for the 68EC020 (A1200), each with CPU_TYPE a constant (m68kcpu.h), so neither
  tests the CPU type at run time; both sets and their cycles are const (flash),
  m68k_set_cpu_type() copies the running one into the SRAM m68ki_handlers[] (the
  index table is shared); each set has its own SRAM handlers.
  `amiga_set_cpu()` / the bench's `--cpu020` pick it, at 14 MHz (A.cpu_mul 2). To
  re-check the CPU: build Musashi's test/test_driver.c (and gen/m68kops_020.c,
  `void amiga_cpu_reset_instr(void) {}`) against this tree with the CPU type
  patched to 68000 and run test/mc68000/*.bin (59/60 pass; move.bin fails the
  same way on stock Musashi in 68000 mode), patched to 68EC020 and run
  test/mc68040/*.bin (18/18: they test the 020 instructions). A Musashi config
  bug made the EC020 decode (d8,An,Xn) as a 68000 (CPU_TYPE_IS_010_LESS counted
  it in with the 68010 off; fixed in m68kcpu.h).

## Chipset findings

- **Fetch units are 8 cc in BOTH resolutions** (hires = two words per plane per
  unit), and the unit starting at or after DDFSTOP is the last one. AROS uses
  hires DDF $3C/$D0 for a 640-px screen; a "units = (stop-start)/4 + 2" hires
  formula gives 39 words and a sheared picture.
- **Instruction fetch reads a window, not the memory map** (AMIGA_FETCH_WINDOW,
  m68kcpu.h / mem.c): m68ki_read_imm_16/32 read the block the code runs in
  (chip RAM, a ROM: the run of 64 KB banks that are one copy of it; one bank
  until 2026-11-10) straight from its RAM / ROM; a miss goes through
  m68ki_fetch_slow16, which moves the window (m68k_set_fetch_window); map() /
  map_low() close it. Musashi's test
  driver builds without it. The window lives in m68ki_cpu_core (its address is in
  a register in every handler, so a fetch loads no literals), ADDRESS_68K is the
  constant 24-bit mask, m68k_execute counts instructions in a register, and the
  68020 instruction-cache tags (`--bus-tune 255,C`) are compiled into the bench
  only: a word fetch on the board went from ~27 instructions to ~13 (2026-11-09,
  Roots' 8-plane part: 1.4 words fetched an instruction, the fetch was the single
  biggest bucket of the PC profile).  Tried the same evening and reverted, each
  measured against the previous firmware in Roots' first 15 s under "With cache":
  a 32-bit opcode fetch keeping the other half for the next word (half the XIP
  transactions for straight-line code) and a chip-RAM-first data callback with
  no bank lookup or stack frame - together cpu 12.3-14.2 -> 13.3-15.5 ms, so an
  XIP cache HIT costs about an SRAM access and the bookkeeping outweighed it; an
  8 KB SRAM hash of the 128 KB opcode -> handler index (flash) went out with
  them (its own A/B is the 19:54 log against the firmware after it).  What the
  PSRAM costs the CPU is its misses (the demo's data, 14-26k a frame), not the
  hits.
- **The handlers see the CPU state in registers** (2026-11-10; m68kregs.h,
  m68krun.h, m68kcpu.h's "two views").  gen/m68kops.c starts with m68kregs.h:
  GCC global register variables for the base of m68ki_cpu, REG_PC, the cycles
  left and REG_IR (r11, r10, r9, r8 on the board; r15-r12 on an x86-64 host, so
  the PC tests run the same scheme; any other compiler or M68K_NO_REGVARS: the
  memory copies).  Only the handler sets are compiled that way.  m68kcpu.c, the
  emulator and every callback see m68ki_cpu.pc / .ir and m68ki_remaining_cycles,
  which are current outside m68k_execute() and inside a memory callback:
  m68krun.h's accessors store the registers before one and load PC and cycles
  after (M68KI_SAVE / M68KI_LOAD), so m68k_cycles_run(), m68k_end_timeslice()
  and a bus error pulsed from a callback work as before.  Rules that follow: a
  new function a handler calls that reads or changes the PC or the cycles from
  outside gen/m68kops.c needs the same pair around the call; nothing in a
  handler set may be called from outside but through m68ki_run_* (they save
  and restore the caller's registers); m68k_in.c must use REG_PC / GET_CYCLES()
  / SET_CYCLES(), never m68ki_cpu.pc or m68ki_remaining_cycles.
  The loop is m68krun.h's m68ki_loop, one per handler set, in the set's SRAM
  window: 18 ARM instructions a turn, written in assembly for the board (GCC
  made 25 of the C version, which the hosts and the bench's AMIGA_STATS build
  run); the offsets it uses are _Static_assert-ed.  Slot 0 of the handler
  table is m68ki_op_illegal_cycles, so the loop takes every handler's cycles
  from m68ki_handler_cycles[] without a test.
- **Trace runs in a loop of its own** (m68ki_run_traced_*, Musashi's loop as it
  was): the plain loop does not look at the trace flags.  m68k_execute() picks
  by FLAG_T1 | FLAG_T0; an instruction that sets one (m68ki_trace_changed() in
  the SR setters) ends the plain loop by taking its cycles away (kept in
  m68ki_trace_rest, given back by m68k_execute(), which goes on in the traced
  loop; m68k_end_timeslice() drops them).  host/tests/make_trace_adf.py is its
  test: 15 traces under T1 on both CPUs, 6 under T0 on the 68EC020 ("TRACE PA" /
  "TRACE PG"), the same counts and final state as the old loop.
- **RAM and ROM data accesses do not go through the callbacks** (m68krun.h's
  m68kf_r8..w32, mem.c's fast_bank): m68ki_cpu.fast[256] has, per 64 KB bank,
  the host address of the bank's address 0 for reads and for writes (NULL: I/O,
  nothing, a ROM's writes - the callback runs).  A bank is in it only if its
  block is 64 KB or more and it is chip RAM exactly below M68K_FAST_CHIP_TOP
  ($200000): the accessors count an access below that for the chip bus model
  (m68k_fast_data(), added to A.bus_data in bus_wait) and pass a chip RAM write
  to the copper list mirror only when its 4 KB page is marked in
  m68ki_cpu.fast_wmap[] (copper.c's mir_set keeps the counts; it was three
  window compares on every chip write).  The tables are in m68ki_cpu so the
  handlers need no address for them (+2.5 KB of SRAM, which the smaller
  handlers give back: the two sets shrank by 2.4 KB, .text by 39 KB).
- **What it gave, counted** (tools/m68kbench: the core with the firmware's
  flags on a Cortex-M33 under QEMU, a TCG plugin counting ARM instructions by
  function from a snapshot of the host bench; no XIP / PSRAM misses in it):
  ARM instructions per 68k instruction, before -> after, "With cache": Roots'
  zigzag 76.6 -> 52.8 (loop 32.6 -> 21.7 with the per-slice entry, handlers
  23.6 -> 21.5, memory 17.9 -> 8.6), its 8-plane part 99.7 -> 63.6, A-Type 98.9
  -> 67.0, Roswell 69.9 -> 49.8.  Every step but the last was bit-identical to
  the old core (final snapshots of 14 runs on the PC, chip RAM and framebuffer
  CRCs of 4 on the Cortex-M33; Musashi's suites as before, also without the
  register variables).  The last, the fetch window as a block, changes the
  A1200's chip bus count: a window move in chip RAM counts as a chip access
  (mem.c, as before), and there are fewer moves - Roots under "With cache"
  runs 0-6% more instructions a frame (11% in the frames of the 8-plane part
  measured, where 9% of the instructions had moved it), the parts start on the
  same frames, audw is unchanged; with the bus model off and on the 68000
  machines it is still bit-identical.  NOT measured on the board yet.
- **The handlers' PC is a host pointer** (M68KI_PCPTR, 2026-11-10 evening;
  m68kcpu.h "The PC as a host pointer", m68krun.h).  REG_PC points at the next
  instruction word in the fetch window's memory, so a fetch is a load and an
  add, and the loop is 13 instructions a turn (was 18; the window check was 5
  of them and 7 more per extension word).  What makes the unchecked fetch safe
  is where an instruction may BEGIN: every PC write that is not "the next word"
  is checked (m68ki_set_pc() for jumps, m68ki_pc_check() after a relative
  branch) against the window less M68KI_PC_GUARD bytes at its end, and the loop
  runs at most M68KI_PC_BUDGET (128) instructions of at most 24 bytes before
  its caller looks at the PC again (m68kf_pc_enter(), every m68ki_run_* call).
  A target outside that part - another block, the window's end, no block -
  gets a pointer that only stands for the address and ends the loop
  (m68kf_break(): the cycles left are put aside as for a trace flag);
  m68kf_pc_enter() then moves the window (m68k_fetch_window(), mem.c: at the
  next instruction, which is when the old fetch moved it, so the chip bus
  counts are the same), gives a smaller budget near a block's end, and for the
  last 48 bytes of a block or memory that is no block copies the instruction
  to m68ki_cpu.stage (m68k_fetch_stage(), no side effects) and runs that one.
  Names: REG_PC is the pointer (only `+=` / `-=` inside an instruction),
  M68KI_PC() the 68k PC (pointer - pc_bias), M68KI_PPC() the instruction's
  address (the loop stores the pointer in ppc_h; a jump moves it with the
  bias), M68KI_SET_PC(v) a jump; m68k_in.c and m68kcpu.h use those, and a
  REG_PC read as a number does not compile.  A callback that changes the PC or
  the memory map is seen by M68KI_LOAD.  An instruction must not fetch after
  it has changed the PC (none does).  Without the fetch window (Musashi's test
  driver) REG_PC is the 68k address as before.
  Bit-identical to the commit before it (the same 14 host runs, 4 on the
  Cortex-M33); Musashi's suites also pass through this path with every
  instruction staged (the driver given AMIGA_FETCH_WINDOW and no window) and
  without register variables.  tools/m68kbench, ARM instructions a 68k
  instruction: Roots' zigzag 52.8 -> 45.6, its 8-plane part 63.6 -> 58.2,
  A-Type 67.0 -> 61.0, Roswell 49.8 -> 43.1.  What a slice costs to enter and
  leave (m68k_execute + m68ki_run_* + m68kf_pc_enter: ~100 instructions, a
  slice being ~20 68k instructions) is now 5 of those 45.  NOT on the board yet.
- **Musashi samples interrupts only on entry to m68k_execute()** (and on SR
  writes): `amiga_update_ipl()` calls m68k_end_timeslice() when the level rises
  inside the CPU, otherwise an interrupt would wait for the end of the slice.
- **HAM in lowres has its own loop** (denise.c ham_plain, 2026-11-10): the
  colour in a register, the pixel straight into the DIRECT row, for the
  columns no sprite covers; the general loop (output_ham_px: hires, under
  sprites, outside the framebuffer) is in flash.  Roots' plasma is HAM6 full
  screen: 47 -> 10 ARM instructions a pixel (HAM6 through a 64-entry table of
  keep-mask / set-bits, ham6_run; HAM8 by arithmetic); before, a drawn frame
  was ~24 ms of the render core and the board skipped four frames in five.
- **Blits without shift, mask or fill have their own loop** (blitter.c
  area_plain, 2026-11-10): the minterm on the words as chip RAM stores them,
  the rows through pointers, a channel that is off or not looked at a constant
  with stride 0; it also took over the old clear / copy path.  Roots' plasma:
  128 blits of D = A | B | C a frame, 108 -> ~55 ARM instructions a word.  Its
  own function at -Os: inlined at -O2 it cost 1.4 KB of SRAM.
- **The slices are merged while the copper waits** (amiga.c run_line,
  2026-11-10): a slice costs ~330 ARM instructions whatever runs in it, so
  from the second one on it is as long as the copper's next move
  (copper_next), a running blit's end and the line allow, always ending on the
  32-clock grid; the CPU cuts it (amiga_slice_cut) when it starts a blit or
  writes COPxLC / COPJMP / DMACON.  The state is then what the short slices
  made it, bit for bit - checked on five runs with idle.c switched off in both
  builds (idle.c notices a loop a slice later, a few cycles' difference).
  What it took to get there, each one a dependence on where slices end:
  Musashi's STOP gave the rest of the slice away even when m68ki_set_sr had
  just taken a pending interrupt (exec's idle STOP, the handler a slice late);
  amiga_now() dropped cpu_rem (a CIA timer one tick off on the 68EC020); after
  a cut the CPU must still be run to the shortened end.  The bus model
  (bus_wait) sums a long slice by stretch - before, in and after the bitplane
  fetch - and a blit keeps the short slices under it (the CPU ran ahead of a
  bus it did not have: Roots' plasma lost 4% of its instructions to busy-flag
  polls).  With it Roots' parts run within 3% of the instructions they had,
  the music at the same rate, pictures a few frames out of phase.  QEMU, ARM
  instructions a frame: zigzag -3.5%, 8-plane part -5.5%, plasma -0.8%,
  sprite part 0; SRAM +752 bytes.
- **Musashi's trace emulation must stay on** (`M68K_EMULATE_TRACE`): trace-vector
  decoders decrypt code one instruction at a time from the Trace exception. With it
  off, Cannon Fodder's disk 2 code spun forever with SR.T set (black screen).
- **Display writes render first, then apply**: `denise_write()` queues the
  write with its hpos and the consumer renders up to it before storing.
  Anything that changes what is on screen must go through it (CPU and copper
  writes carry their own hpos).
- **Denise runs as an event consumer** (denise.c, the queue at the end): the
  scheduler's line start/end, frame start and display writes are queued with
  the state they read (vpos, DMACON, LOF), and replayed by two stages with
  their own cursor and lock: fetch (bitplane DMA into a 4-line pf ring) and
  output (colours, sprites, framebuffer), which follows it and may be on the
  other core. Each keeps its own copy of BPLCON0 and DIW. Sync mode replays at
  once (host bench, smoke); the firmware turns on `amiga_render_async`, core 1
  pumps (`amiga_render_pump()`, 32-cc steps, between line builds on PICO_DV)
  and core 0 takes a stage itself whenever it would wait;
  `amiga_run_frame()` waits for both at frame end. The chip RAM reads (bitplane
  and sprite DMA) are the emulation's, at the event's time (`dma_*` in denise.c):
  the words reach the fetch stage through a 16 KB ring (`ws[]`, 40-80 lines of
  lead) and the sprites' through events. Read by the stages instead, they showed
  what the game wrote after the beam: IK+ erases its fighters ~50 lines behind
  it and flickered. Bounding the emulation's lead instead (8 lines) cost the
  overlap and slowed Cannon Fodder's intro scroll. Every queued write first runs
  the DMA side up to its hpos (`dma_to` in denise_write): the event lets the fetch
  stage go that far, and the ring must hold those words by then (sprite register
  writes skipped it: RoboCop 2's last playfield line got stale words in sync mode,
  and could in async). `--render-thread` screens must
  match the sync ones (IK+, Cannon Fodder, Exolon checked frame for frame). `pico-amiga-host --render-thread`
  runs the async path on a thread; its screens must match the sync ones.
- **ECS super-hires** (denise.c): a pf entry is a pixel pair (left bits 0-1,
  right 2-3) and the LUT gives the pair's colour: COLOR[p2*4+p1], the left pixel
  its top two bits per gun, the right its low two (WinUAE's linetoscr_*_sh),
  averaged into one of our 720 pixels. graphics.library lays the palette out
  for exactly that (Workbench blue $68B shows as $5AA: 64 colours, correct).
  Pixels start at DIW x 2t + 5 (lowres 17, hires 9): with KS 2.04's DDF
  $38/$D8, Workbench's last column lands on output pixel 679 as in hires.
- **FLOPPY_TURBO scales the index pulse too, while a DMA runs** (floppy.c): the
  drive spins faster, so a transfer spans as many revolutions as on hardware.
  Barbarian's loader stops a two-revolution read on the third index; with
  only DSKBLK scaled its index handler stayed on the level 6 vector and the OS
  hung in a storm of uncleared EXTER interrupts (black screen).
- **A read cut short leaves the head where the time took it** (floppy.c
  abort_read): the words are handed over at the DMA's start, but a DSKLEN write
  that stops it puts rot_pos at start + the words that read time covers.
  RoboCop's loader looks at a sector's header and restarts at once for a sector
  it does not want; with the head at the read's end it saw every other sector.
- **A swapped disk must be seen gone** (floppy.c, SWAP_LINES): Kickstart polls
  /CHNG now and then, and the menu swaps with no emulated time in between, so
  the core keeps the drive empty 2 s before the new disk is in (KS 1.3 needs
  ~0.5 s). Without it Dune II asked for a disk that was already in DF0.
- **Gayle (A600, gayle.c) is WinUAE's map**: Gayle's bank $D80000-$DDFFFF answers
  only with A19 and A17 set ($DA/$DB), the ID ($D0, the AGA one $D1) is shifted
  out one bit per byte read of $DE1000 (bit 7) and a write restarts it, the CIAs
  sit at $BF0000 only (no mirror at $A00000: the PCMCIA space), nothing at
  $C00000-$D7FFFF, no clock. An empty IDE port reads $7F in the status register
  and $FF elsewhere (WinUAE's "IDE killer"): KS 2.05 writes $12 to the cylinder
  register, reads $FF back and boots at once instead of waiting ~30 s.
- **Fast RAM is a Zorro II autoconfig board (mem.c, WinUAE's expansion.cpp)**:
  er_Type $E0 | size (Zorro II, memory, linked into the free list), the other
  registers inverted nibbles; Kickstart writes $4A then $48 (the base, $200000)
  and the board maps there. Any reset and the RESET instruction unconfigure it:
  ColdReboot (WHDLoad's quit) runs RESET, then the ROM configures it again.
  Snapshots keep the base (MEM's end) and the contents (FAST).
- **AGA (A.aga; the firmware's A1200, the bench's `--aga`)**:
  Alice $23 / Lisa $F8; Lisa's 256 colours - the producer (denise_write) resolves
  BANK, drops LOCT writes (low nibbles: the 12-bit output does not show them) and
  RDRAM, and queues the entry in the event's x; BPLCON4 (BPLAM, ESPRM); FMODE: the
  fetch unit and words per plane from WinUAE's fetchunits[], the pixels at DIW x
  2t + 2 x fm_maxplane + 1 (17 / 9 / 5 without FMODE; hires FMODE 3 = 17); 8 planes;
  HAM8 (control in planes 1-2) and HAM in hires. SSCAN2 / BSCAN2 (31 kHz modes) not.
  Workbench 3.1 on AGA writes FMODE 3 at line 43, not at the frame's start.
- **The A600's IDE (ide.c) hands sector bytes over in order, IDENTIFY as a PC
  holds it** (little-endian words, strings' first character in the high byte -
  WinUAE's pw/ps): Gayle's wiring makes the 68000 see IDENTIFY's numbers
  byte-swapped and scsi.device swaps them back. Built big-endian, KS 3.1 read 16
  heads as $1000, sent INITIALIZE DEVICE PARAMETERS with select $FF (the slave)
  and hung. A bare-partition HDF gets a virtual RDB (WinUAE's: 32 blocks per
  track, 1 surface, 2 reserved, the image from block 32). The hard disk can also be
  an SD partition (pico-speccy's raw IDE window, ide_mbr.h; machine.cpp), never
  writable over the card's own FAT volume; the PC firmware takes `--sd card.img`.
  Two drives (master, slave: `amiga_set_hdf(unit, ..)`, the bench's `--hdf2`) share one
  task file and one transfer - a command runs on the drive bit 4 of the select
  register names; with one drive the other's status reads $01 and its registers 0
  (WinUAE's absent half of a pair), whichever of the two it is. A bare partition
  on the slave is DH1 in its virtual RDB (two DH0s would be renamed by the boot).
- **FFS validates a new partition in RAM**: Format in 2.x writes the root block with the
  bitmap flag clear and FFS builds the bitmap at the first mount, holding blocks/8
  bytes at once. A 2 GB Work (4.17M blocks, ~520 KB) on a 1 MB A600 reports "Volume
  Work is not validated" and stays so; 100 MB works, and 2 GB does with 2 MB of chip
  RAM (`--a601`): partitions of ~500 MB at most on a 1 MB machine.
- **Every connected drive costs Kickstart memory**: Dune II (1 MB) reports a
  "Memory Allocation Error" with 4 drives (Floppy drives Auto on its 5-disk
  set) and runs with 1 or 2; the message is drawn while its palette is black.
- **Sprite DMA follows VSTART/VSTOP from any source** (denise.c sprite_dma): the
  first control words are fetched on line 25 only, with sprite DMA on then; a
  sprite otherwise waits for its VSTART, also one written to SPRxPOS/CTL by the
  CPU or copper. RoboCop 2 writes POS/CTL and data pointers in the vertical blank
  and turns sprite DMA on later; fetching control words at the first DMA line
  made RoboCop invisible (and the title's icons garbage).  The fetch happens
  after colour clock 32 of the line (SPRITE_DMA_CC in amiga.c: the slots are
  $15-$34), not at line start: Roots' sprite part fetches its 8 x 64-pixel
  sprites' one data line at 28 and has the copper clear SPREN at clock 16 of
  line 29 - at line start the fetch went on and read the next sprite's control
  words as data; the screen (the sprites' constant columns, coloured by the
  copper's palette stream and BPLCON4 banks) was vertical bands (2026-11-09).
- **BPLCON4 takes effect one lowres pixel after its write's colour clock**
  (con4_pending in denise.c); the other registers' writes at the clock itself.
  Roots' sprite part switches banks every 48 pixels at the column where a sprite
  period starts (sprite x = HSTART + 1): applied at the clock, each period's
  last pixel showed the next bank's colour, a thin line down every block border.
- **AGA BPLCON1 has scroll bits 16 and 32** (PF1H6-7 bits 10-11, PF2H6-7 bits
  14-15) for the wider fetch units, wrapped at the unit's width (fetch_unit):
  Roots' zigzag / rings / rays part scrolls odd and even planes 0-63 a line with
  FMODE 3 (eight plane pointers, BPLCON1 and BPLCON4 per line); with the four
  classic bits alone its patterns were a dense weave of 16-pixel cells.
- **A colour written to an entry nothing shows is applied without drawing up
  to it** (o_step, color_shown: AGA plain single playfield - the playfield's
  v ^ BPLAM entries, the armed sprites' ESPRM / OSPRM banks, COLOR00).  Roots'
  sprite part streams 44 colours a line into the banks it shows later: 9,400
  output ranges a frame became 3,600, the frames byte-identical.
- **A blit's start clears the B shifter's previous word** (blitter.c, BLTSIZE /
  BLTSIZH): a BLTBDAT the CPU writes afterwards is shifted against 0, as
  WinUAE's fast path starts each blit with prevb = 0.  Sanity's Arte draws its
  logo morph as 1-word columns 480 words tall, ORed in with ASH = BSH and
  BLTBDAT = $FFFF written before each blit: the shifted $FFFF is the mask that
  drops what the A shifter carries over from the previous row (the latches are
  not cleared between rows); shifted against the previous blit's $FFFF the mask
  was $FFFF and the logo came out in shards (2026-11-09).
- **The vertical window a line's bitplane DMA follows is the one at its
  DDFSTRT** (denise.c vwin_apply): a DIWSTRT / DIWSTOP written before the
  line's DDFSTRT counts for the line, one written after it from the next line.
  Arte's "ARTE" picture puts the vblank setup (DIWSTRT $2981) on line 32 and the
  picture's DIWSTRT $1D81 and plane pointers at colour clocks 114-170 of the
  same line: fetched on line 32 after the writes, the five planes started 5-9
  words apart and the picture was shredded.  (At line start alone, the line was
  in the window from the previous frame's $1D81; WinUAE's equality compare at
  line start would fetch too - the picture says the hardware does not.)
- **Known: a snapshot loaded in Roots jumps to its sprite part** within three
  frames, from the rings or the zigzag part alike (the bench's --state-load);
  the bench's straight runs are deterministic (t4800.png == f4800.png).
  Something the demo polls is restored as "skip" - not found yet.
- **Bitplane DMA follows DMACON mid-line** (custom.c -> denise_write(R_DMACON)):
  off stops the line's fetch (no modulo), on fetches the units from there. A-Type's
  panel turns it off on its first line, rewrites the pointers after DDFSTRT and turns
  it on on the next; sampled at line start only, planes 4-5 lagged a word (a grey
  shifted copy of PUSH RUN BUTTON, scrambled ship icons).
- **Reading COPJMP1/2 strobes them** (custom_read): Zynaps starts its list with
  `move.w $dff088,d0`; ignored, the OS list ran on and its last MOVE (BPLCON0 =
  0 planes) left the intro and the game black.
- Single playfield sprite priority uses **PF2P**, not PF1P (vAmiga agrees).
- **The copper's list is mirrored in SRAM** (copper.c, amiga_int.h: COP_MIR_N =
  2 windows of COP_MIR_SIZE = 12 KB): fetches are counted by 4 KB block with a
  decay of ~8 frames, the windows go to the two non-overlapping 12 KB ranges with
  the most, a range taking a window once it has been in that top set 3 frames
  running (COP1LC is no guide: Roots and Arte start with a stub that jumps to the
  real list; Roots' zigzag part alternates two 20 KB lists every frame, which is
  why there are two windows and the slow decay - a per-frame ranking put both
  windows into that frame's list and the candidate never settled).  Every chip
  RAM writer keeps them current - the CPU in mem.c's bank path, chip_ww for the

- **The playfield ring holds one entry per pixel of the line's resolution**
  (denise.c pf_ring): a lowres line's pixel x is pf_o[x], a hires line's pair

- **Frame skipping** (amiga_set_render_skip; main.c: Video > Picture > Skip frames

  up to 4 in a row, so the emulation holds 50 frames a second and a drawn frame

  frame's), the fetch stage spreads nothing, the output stage takes no framebuffer
  row (fbrow NULL).  The frame's display writes are not queued: the last value of

  (the next frame fetches its control words again).  Roots' sprite part makes

- **Sprites are composed for the columns being drawn** (sprites_to from output():
  a sprite register write or DMA starts an epoch - the armed sprites' words are
  expanded once, four 2-bit values a lookup (spr4) - and each output range then
  composes only its columns, the pair's spl[] byte by table (spr_tab)).  Roots
  repositions its 8 x 64-pixel sprites 3-4 times a line (1,100 times a frame): the

- **Busy-wait loops are not run** (idle.c, from cpu_until once a slice): `dbra Dn,*`
  comes off Dn exactly; a test + Bcc back to it (cmpi / btst #n / tst on abs.w, abs.l,
  (d16,An)) found at two slice ends with its value unchanged skips whole slices while

- **The CD32 is Akiko at $B80000 on the A1200's chips without Gayle** (akiko.c, after
  WinUAE's akiko.cpp; cfg.akiko, the bench's `--cd32 --rom kick40060.CD32 --ext
  kick40060.CD32.ext --cd x.cue`). The drive is a byte protocol through two 256-byte
  rings in chip RAM (commands at base + $200, replies at base); sectors arrive by
  DMA into 4 KB blocks, the highest PBX bit first (Lotus 3 needs that order), as
  the raw 2352 bytes with the first four replaced by a counter - the platform's
  read callback puts the 2336 bytes after the header straight into chip RAM
  (cdimage.c: `.iso`, or a `.cue` with BINARY files of 2048 / 2336 / 2352 bytes a
  sector; Cannon Fodder's second track is MODE2/2336 behind a 3 s PREGAP). One
  sector a 1/75 s (1/150 at double speed), counted in lines; no cache, no thread.
  The TOC goes out one entry a sector time after a seek to before the disc. A long
  access to Akiko is ONE access (akiko_read32 / write32 from mem.c): the C2P
  register counts accesses, two word halves would step it twice. The NVRAM is a
  24C08 bit-banged on $B80030 (1 KB of the platform's; machine.cpp keeps it in
  /pico-amiga/cd32.nvram). The pad (port 2): POTGO pin 5 as an output and low
  makes it a shift register clocked by CIA-A PRA bit 7, read on POTGOR bit 14 -
  blue, red, yellow, green, forward, reverse, play, then 1, then 0s. CD audio
  (akiko_audio, from paula_half_line): the disc's 44100 Hz frames a sector at a
  time through amiga_cd_t.audio (a pointer into the platform's memory: the
  firmware's read-ahead buffer), the nearest frame for each 31300 Hz sample, at
  half level over Paula's, clamped; its sector follows play_pos (both counted
  from the lines). Checked with a made-up tone disc only (smoke), no game yet.
